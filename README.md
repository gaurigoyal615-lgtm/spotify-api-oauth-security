# spotify-api-oauth-security

A learning project to understand OAuth 2.0 Authorization Code Flow with PKCE, server-side session management, token handling, and secure access to the Spotify Web API using Flask.

The goal is to build the authentication flow step by step while understanding the security decisions behind each component.

## Project Goals

- Understand OAuth 2.0 Authorization Code Flow with PKCE.
- Implement the login and authorization callback flow.
- Understand OAuth `state` validation and CSRF protection.
- Store session data on the server using Redis and Flask-Session.
- Handle access tokens, refresh tokens, and token expiration.
- Access protected Spotify Web API endpoints.
- Learn how to handle API errors and improve application security.

## Tech Stack

- **Python** — application logic
- **Flask** — web application and routes
- **Spotify Web API** — authorization and API access
- **OAuth 2.0 with PKCE** — authorization flow
- **Redis** — server-side session storage
- **Flask-Session** — server-side Flask sessions
- **python-dotenv** — loading local environment variables
- **Requests** — HTTP requests to Spotify

## How the Authentication Flow Works

The application uses the Authorization Code Flow with Proof Key for Code Exchange (PKCE).

PKCE helps protect the authorization code from being used by an attacker who intercepts it. Instead of relying on a client secret, the application creates a temporary secret called the `code_verifier` and proves possession of it during token exchange.

### Step-by-step flow

1. **User visits `/login`.**  
   The Flask application generates a random `state` value and a `code_verifier`.

2. **Generate the code challenge.**  
   The application hashes the verifier using SHA-256 and encodes the result using Base64URL, removing the trailing padding.

   `code_challenge = BASE64URL(SHA256(code_verifier))`

3. **Store temporary OAuth values.**  
   The `state` and `code_verifier` are stored in the server-side session. The verifier should not be sent in the authorization URL.

4. **Redirect to Spotify.**  
   The application redirects the user to Spotify's authorization endpoint with the client ID, redirect URI, requested scopes, state, code challenge, and `S256` challenge method.

5. **User grants or denies access.**  
   Spotify displays the consent screen and redirects the browser to the registered callback URI.

6. **Validate the callback.**  
   The application must handle authorization errors and compare the returned `state` against the value stored in the session. Missing or mismatched state should cause the request to be rejected.

7. **Exchange the authorization code.**  
   If validation succeeds, the application sends a POST request to Spotify's token endpoint with the authorization code, client ID, exact redirect URI, and original `code_verifier`.

8. **Spotify validates PKCE.**  
   Spotify checks that the verifier matches the challenge associated with the authorization request. If valid, Spotify returns token information.

9. **Store tokens and access the API.**  
   The application stores tokens server-side and uses the access token to request protected Spotify Web API resources.

10. **Refresh expired access tokens.**  
    When implemented, the application will use the refresh token to obtain a new access token without requiring the user to authorize again, subject to Spotify's token and authorization rules.

## Why PKCE Is Needed

PKCE binds the authorization request to the later token exchange.

- `code_verifier`: A random secret generated by the application and retained server-side.
- `code_challenge`: A transformed version of the verifier sent to Spotify during authorization.
- `code_challenge_method=S256`: Tells Spotify that SHA-256 is used to create the challenge.
- `state`: A separate random value used to associate the callback with the login attempt and protect against login CSRF.

The `state` value and the PKCE verifier serve different purposes. PKCE does not replace callback `state` validation.

## Session Management

Flask's default session implementation stores session data in a signed cookie. Signing protects integrity, but it does not encrypt the cookie contents.

This project uses Flask-Session with Redis to store session data server-side. The browser holds a session identifier, while the corresponding session data is stored in Redis.

Temporary OAuth values and tokens should not be exposed in URLs or sent to the browser unnecessarily.

## Local Setup

### 1. Clone the repository

```bash
git clone <your-repository-url>
cd spotify-api-oauth-security
```

### 2. Create and activate a virtual environment

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Configure environment variables

Create a local `.env` file:

```env
SPOTIFY_CLIENT_ID=your_spotify_client_id
FLASK_SECRET_KEY=your_random_flask_secret_key
```

Never commit `.env` or expose credentials in source code. The Flask secret key should remain stable between application restarts.

### 5. Configure Spotify

In the Spotify Developer Dashboard, register this exact redirect URI:

`http://127.0.0.1:5000/callback`

The redirect URI used in the application and token exchange must match the registered URI.

### 6. Start Redis

Ensure a Redis server is running at `127.0.0.1:6379`, matching the application's session configuration.

The Python Redis package alone does not start the Redis server.

### 7. Run the application

```bash
python app.py
```

Open `http://127.0.0.1:5000/login` once the login route is implemented.

## Security Considerations

- Generate OAuth `state` and PKCE verifiers using a cryptographically secure random generator.
- Validate `state` before exchanging an authorization code.
- Keep the PKCE verifier in server-side session storage.
- Never commit environment files, access tokens, refresh tokens, or other secrets.
- Use the exact registered redirect URI.
- Keep tokens server-side and avoid logging sensitive token values.
- Do not confuse OAuth `state` validation with CSRF protection for application forms and POST requests.
- Handle authorization failures and token errors explicitly.
- In production, use HTTPS and appropriately configured secure session cookies.
